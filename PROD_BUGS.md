### Почему №18 отложен

Пререндер на двух языках требует не правки, а фичи: разных URL на язык (`/ru/…`), взаимных
`hreflang`, языкового переключателя, который навигирует, а не только меняет state, удвоенного
пререндера (116 → 232 маршрута в 20-минутном CI-бюджете), удвоенного sitemap и canonical/OG на
каждый язык. Плюс есть предварительное условие, которого нет в самом отчёте: `contentRu.ts` — это
1.5 МБ, который нельзя тянуть в eager-граф (инвариант репозитория и гейт по размеру бандла), а
русский маршрут по определению хочет русский текст на первой отрисовке. Сначала нужно разрезать
`contentRu.ts` по темам — так же, как уже разрезаны `public/seed/answers/<slug>.json`.

Для одного URL на страницу `hreflang` не помогает: это разметка про соответствие *разных* URL.
Так что дешёвого частичного фикса здесь нет — есть либо фича целиком, либо ничего.
Оценка severity (🟢 Low) и принципы репозитория («минимум кода, который решает задачу»,
«никаких полуфабрикатов») говорят: не делать сейчас. Полный план в две фазы подготовлен отдельно.

## 1. 🔴 BLOCKER — Service worker ломает любой URL без завершающего слеша

**Самый серьёзный баг на проде.** У любого вернувшегося посетителя (то есть у всех, кто был на сайте хотя бы раз и получил service worker) навигация на URL без слеша падает с браузерной ошибкой `ERR_FAILED` — «This site can't be reached».

### Как воспроизвести

1. Открыть https://xxx1694.github.io/readytoflutter/ и дождаться регистрации SW (одна секунда).
2. Кликнуть «Roadmap» в сайдбаре. URL становится `…/readytoflutter/roadmap` — работает, это client-side переход.
3. Нажать **Cmd+R / F5**.
4. → `This site can't be reached … ERR_FAILED`.

Проверено в этой сессии, скриншот `.playwright-mcp/shots/29-reload-broken.png`.

### Доказательство, что виноват именно SW

| Состояние | `GET /readytoflutter/roadmap` |
|---|---|
| SW разрегистрирован, кэши очищены | ✅ 200 (301 → `/roadmap/`) |
| SW активен | ❌ `net::ERR_FAILED` |

Переключал оба состояния по два раза — воспроизводится стабильно.

### Причина

GitHub Pages отдаёт `301` на `/roadmap` → `/roadmap/`, потому что пререндер кладёт файл как `roadmap/index.html`.

В `frontend/vite.config.js` навигационный роут переписывает запрос:

```js
requestWillFetch: async ({ request }) =>
  new globalThis.Request(request.url, { cache: 'no-cache', credentials: 'same-origin' }),
```

Навигационный `Request`, который создаёт браузер, имеет `redirect: 'manual'`. Пересобранный через `new Request(url, …)` получает дефолтный `redirect: 'follow'`. Fetch внутри воркера проходит редирект сам, и в ответе стоит флаг `redirected === true`.

По спецификации Service Workers воркер **не имеет права вернуть redirected-ответ на навигационный запрос** — браузер отбраковывает такой ответ и валит навигацию. `handlerDidError` при этом не срабатывает: с точки зрения Workbox запрос отработал успешно, ломается уже на уровне браузера.

Комментарий в конфиге объясняет, зачем понадобился `requestWillFetch` (обход workbox#1796, чтобы GitHub-овский `max-age=600` не держал пользователя на старом билде). Проблема в том, что вместе с `cache` потерялся `redirect`.

### Масштаб

- **114 из 115 URL в `sitemap.xml` отдают 301** (проверил все, гистограмма: 1×200, 114×301). То есть **вся индексируемая поверхность сайта** — каждая тема, каждый стек, roadmap, topics, pricing, contact — не открывается у вернувшегося посетителя.
- Все `<link rel="canonical">` указывают ровно на эти же URL без слеша.
- Все внутренние ссылки приложения (`href="/readytoflutter/roadmap"`) тоже без слеша, поэтому **F5 на любой странице кроме главной = белый экран ошибки**.
- Шпаргалка (`/topic/<slug>/cheatsheet`) доступна только по такому URL — расшаренная ссылка на неё не откроется.

### Как чинить

Сохранить редирект-режим навигационного запроса при пересборке:

```js
requestWillFetch: async ({ request }) =>
  new globalThis.Request(request.url, {
    cache: 'no-cache',
    credentials: 'same-origin',
    redirect: request.redirect,   // 'manual' для навигаций
  }),
```

Дополнительно стоит убрать сам источник редиректов — генерировать в sitemap и canonical URL со слешем (`/roadmap/`), а внутренние ссылки в `lib/routes.ts` привести к тому же виду. Тогда 301 вообще перестанет возникать.

Заодно нигде нет `og:url` — его тоже стоит добавить.

## 7. 🟡 MEDIUM — Лишний 404-запрос `/api/auth/health` на каждой холодной загрузке

На каждой холодной загрузке любой страницы уходит один запрос на `https://xxx1694.github.io/api/auth/health` → **404**, и в консоль падает красная ошибка.

Проверено на чистой загрузке главной: в списке сетевых запросов ровно `[GET] https://xxx1694.github.io/api/auth/health => [404]`.

Отдельно стоит заметить, что путь резолвится от корня origin (`/api/…`), а не от base path — то есть запрос уходит вообще мимо приложения.

### Причина

В `api/api.ts` есть флаг `noBackend`, и `App.tsx:73` его честно проверяет:

```js
if (noBackend) useAuth.setState({ backendAvailable: false });
else useAuth.getState().probeBackend(apiBaseUrl);
```

Комментарий рядом объясняет замысел: «don't spend a request (and a slot on a 3G connection's queue) asking GitHub for /api/auth/health».

Но в `components/AccountMenu.tsx:31-33` стоит собственный mount-эффект:

```js
useEffect(() => {
  if (backendAvailable === null) probeBackend(apiBaseUrl);
}, [backendAvailable, probeBackend]);
```

`AccountMenu` рендерится в `Header` → `Layout` → `App`. **React выполняет эффекты детей раньше эффектов родителя**, поэтому эффект `AccountMenu` срабатывает первым, видит начальное `backendAvailable: null` (`store/auth.ts:47`) и запускает пробу. Эффект `App` выставляет `false` уже после — запрос к тому моменту улетел.

Гард в `App.tsx` на Pages-сборке фактически мёртвый.

**Чинить:** проверять `noBackend` в самом `probeBackend` (или в `AccountMenu`), а не только в `App`.

## Что было сделано

1. **Баг №1** — одна строчка (`redirect: request.redirect`) плюс guard в CI-джобе `repo-invariants`,
   чтобы её нельзя было потерять снова. Это чинило полностью сломанный сайт для всех вернувшихся
   посетителей, поэтому шло первым.
2. **Баги №2 и №10** — превью ссылок и canonical. `og:image`/`twitter:image` абсолютизируются на
   этапе пререндера; canonical везде приведён к форме со слешем — той, которую Pages отдаёт с 200,
   и той, что теперь в sitemap. Canonical добавлен туда, где его не было (`/`, `/pricing`,
   `/contact`, `/knowledge`, шпаргалки).
3. **Баги №3, №4, №5** — общая причина: прод собран без бэкенда, а интерфейс и копирайт про это не
   знали. Вместо удаления функциональности сделана честная развилка по `backendAvailable === false`:
   контакты ведут в GitHub Issues, вход объясняет «этот билд без сервера, прогресс живёт в браузере»,
   а обещания AI-проверки убраны из статики и оставлены условными там, где условность уместна.
   Если бэкенд поднимут (`VITE_API_BASE_URL` в переменных workflow) — все три экрана вернутся сами.
4. **Баг №6** — единственная находка, где пользователю показывали молча неправильные данные:
   теперь для стеков без трека рисуется явный пустой экран, а не роадмап Flutter.

Остальное — по таблице статусов выше. №18 отложен осознанно, с планом.

## Что осталось на потом

- **№18** — двуязычные URL. План в две фазы; фаза 1 (разрезать `contentRu.ts` по темам) полезна
  сама по себе, независимо от SEO.
- **`robots.txt` на project Pages вообще не читается краулерами** — они берут его только с корня
  origin (`https://xxx1694.github.io/robots.txt`), который принадлежит пользовательскому Pages-сайту.
  Путь в `Disallow` теперь корректный, но на этом развёртывании файл всё равно не запрашивается.
  Замечено при починке №12; отдельного решения требует не код, а выбор хостинга/домена.
- **`/stats` self-canonical** указывает на URL, который отдаётся из `404.html`. Сейчас это
  корректно (страница не пререндерится), но если её когда-нибудь добавят в пререндер — canonical
  должен получить слеш в том же коммите.
